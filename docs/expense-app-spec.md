# 経費申請アプリ 仕様書

最終更新: 2026-11-12

## 1. 目的

レシートの写真から経費をすばやく申請し、申請データを **Google スプレッドシートに蓄積**、
**領収書画像を Google ドライブに保存**する。申請者は自分の分、管理者は全員分を
月ごとに見られ、事業部・人・費目ごとに並べ替えて確認できる。蓄積したデータは
実績管理・分析ツールから読み込める。

必要最低限の機能に絞っている。**承認の手続きは無い**（申請はそのまま計上される。
間違いは削除して申請し直す）。

## 2. システム構成

```
[利用者のブラウザ]                         [Google クラウド]
  経費申請アプリ (静的サイト)               ┌───────────────────────────┐
   - 利用コードでログイン                   │ Apps Script Web App       │
   - 画像の縮小（端末内）            ─┐     │  認証・権限チェック        │
   - 申請フォーム                      ├───▶│  doPost: ログイン/申請/    │
   - 月ごとの一覧                      │     │   一覧/アカウント/事業部   │
   - アカウント・事業部の管理          │     │  doGet : JSON（権限別）    │
   - localStorage キャッシュ           │     └───────┬───────────┬───────┘
                                       │             ▼           ▼
                                       │     スプレッドシート   Google ドライブ
                                       │     経費データ/ユーザー/  (領収書画像)
[分析・実績管理ツール] ◀────────────────┘     事業部マスタ
   Looker Studio / BIツール / スプレッドシート集計 / JSON API
```

- フロントエンド: バニラ JS（`expense-app/`：`index.html` / `app.js` / `app.css`）。
  GitHub Pages で公開。レスポンシブ対応。
- バックエンド: Google Apps Script Web App（`apps-script/Code.gs`）。サーバー・GCP設定不要。
- データストア（1つのスプレッドシート内。タブ名・見出しは日本語）:
  - **経費データ** = 申請（1申請1行）
  - **ユーザー** = アカウント（パスワード・利用コードはソルト付き SHA-256 ハッシュ）
  - **事業部マスタ** = 事業部の一覧
  - Google ドライブ「経費領収書」フォルダ = 領収書画像（行に URL を保持）

## 3. 認証・権限

### 3.1 利用コードとログイン

- 利用者は、管理者が発行する **8桁の利用コード**（例 `ABCD-EFGH`）だけでログインする。
  紛らわしい文字（0/O・1/I）は使わず、小文字・ハイフン・空白は吸収する。
- コードはパスワードと同じ列にハッシュで保存する。**表示されるのは発行した直後の1回だけ**
  （忘れたら再発行する）。再発行すると前のコードは使えなくなり、パスワードもそのコードに
  置き換わる。
- 管理者は「IDとパスワード」でもログインできる（最初の管理者の作成・緊急用）。
- 管理者が「案内文をコピー」で作る案内文のリンク（`/#api=<URL>&code=<コード>`）を開くと、
  接続先の設定もコードの入力もなしでログインできる。`#` 以降はサーバーへ送られず、
  読んだらすぐアドレスバーから消す。
- ログイン失敗のたびに1秒待たせる。コード形式（8桁）でない入力は照合しない。

### 3.2 トークン

- ログイン成功で **HMAC-SHA256 署名付きセッショントークン**（有効期限30日）を発行する。
- 起動時に残りが半分を切っていれば新しいトークンを返す（使い続けている間は切れない）。
- トークンにはソルト由来の世代を入れてあり、**コードの再発行・パスワードの変更で、
  それ以前のトークンはすべて失効する**。無効化した利用者も、次のリクエストで弾かれる。
  自分自身のコードやパスワードを変えたときは、新しいトークンを返して締め出さない。
- 以降のリクエストはトークンを必須とし、サーバー側で毎回検証する。

### 3.3 権限

| ロール | できること |
| --- | --- |
| `user`（一般） | 申請、自分の申請の閲覧・削除 |
| `admin`（管理者） | 全員の申請の閲覧、全件の削除、利用者・事業部の管理 |

申請者名・申請者IDはサーバー側でセッションから強制する（なりすまし防止）。
最初の管理者は、管理者がまだ一人もいないときの「最初の管理者を作る」画面
（`setup`）で作る。それまで（「ユーザー」シートが空の間）は認証なしの互換モードで動く。

## 4. 機能要件

### 4.1 申請（画像のAI読み取り）

- レシート／領収書画像を選ぶ（**画像は任意**）。長辺1600pxに縮小して送る。
- **AIが日付・金額・費目・支払先・摘要を読み取り**、フォームへ自動入力する。
  確認して修正し、「申請する」で保存する。読み取れなかった項目は手入力する。
  AIが使えない・失敗した場合は、画像を添付したまま手入力で申請できる。
- プロバイダは設定で選ぶ:
  - **Gemini（推奨・無料枠可）**: `GEMINI_API_KEY`。モデルは `GEMINI_MODEL`
    （未設定なら現行の flash 系の別名を順に試し、全滅したらそのキーで使えるモデルを調べて再試行）。
  - **Claude**: `ANTHROPIC_API_KEY`。モデルは `OCR_MODEL`（既定 `claude-opus-5`）。
  - 両方あるときは Gemini 優先（`OCR_PROVIDER` で切替）。
- **段階的な読み直し**: 1回目は速度優先の行数（`RECEIPT_RAW_TEXT_MAX_LINES`）で読み、
  **金額か日付が取れなかったときだけ**行数を増やして（`RECEIPT_RAW_TEXT_RETRY_LINES`）
  読み直す。既定では同じプロバイダなので追加の課金はない。`OCR_ESCALATE_PROVIDER` を
  設定したときだけ、読み直しを上位プロバイダへ回す。**AI呼び出しは1リクエストにつき最大2回**。
- 費目: 交通費 / 交際費 / 会議費 / 消耗品費 / 通信費 / 宿泊費 / その他。
- 事業部は、自分に割り当てられた事業部から選ぶ（初期値は先頭）。割り当てが無い人は
  全事業部から選ぶ。1つの申請に付く事業部は1つ。

### 4.2 一覧

- **月ごと**に表示する（「全期間」ボタンで月を空にすると全期間）。一般ユーザーは自分の分、
  管理者は全員分。
- 並べ替え: 日付 / 月ごと / 事業部ごと / 人ごと / 費目ごと / 金額。「〜ごと」のときは、
  まとまりごとの件数と小計を出す（月ごとは新しい月から、それ以外は小計の大きい順）。
- **領収書の画像**: 画像のある申請には、一覧に小さな画像（ドライブの縮小画像 `w160`）が出る。
  タップすると大きく（`w1600`）表示し、**いま並んでいる順**に前後の領収書へ移れる
  （← → キー・ボタン・スマホは左右のスワイプ。Esc・背景のタップで閉じる）。
  「Googleドライブで開く」リンクから原本も開ける。画像が開けないとき（共有が外れている等）は
  一覧では 🧾 になり、拡大画面には案内が出る。
- 削除: 一般ユーザーは自分の申請だけ、管理者は全件。画像もゴミ箱へ移す。
- 過去に却下された申請（`rejected`）は、取り消し線で表示し、合計に含めない。

### 4.3 アカウント・事業部の管理（管理者のみ）

- **利用者の追加**: 名前・事業部（複数可）・権限を入れて追加すると、利用コードが出る。
  「案内文をコピー」で、本人へ送る文面（コードとログイン用リンク）を作る。
- **利用者の一覧**: 事業部の割り当ての変更、コードの再発行、無効化・有効化。
  自分自身は無効化できない。
- **事業部マスタ**: 追加・削除。削除しても、過去の申請や利用者に付いている事業部名は残る
  （選択肢から外れるだけ）。初期値は BAR / 人材 / 運送 / 本部 / ARTGRAGE / クリニック /
  GoonerHouse。
- 利用者の事業部は、シートに `人材,BAR` のようにカンマ区切りで複数入る。

### 4.4 領収書の保管（Google ドライブ）

- フォルダ体系: `経費領収書/<事業部>/<yyyy-MM>/`。事業部未設定の申請は「未設定」フォルダへ。
- 事業部フォルダ・月フォルダは申請保存時に自動作成する。`setupMonthlyFolderTrigger()` を
  一度実行すると、毎月28日に翌月分のフォルダを全事業部へ事前生成する（任意）。
- **ファイル名**: `日付_申請者_採番.jpg`（例 `2026-07-15_山田太郎_001.jpg`）。
  採番は同じ日付・同じ申請者の中で001からの連番。
- 画像は保存時に「**リンクを知っている人は閲覧可**」にする。しないと、所有者以外の
  ブラウザからはリンクが開けない。**URLを知っていれば認証なしで閲覧できる**ので、
  この扱いが許容できない運用では `shareReceiptFile_` の中身を空にする。

### 4.5 起動と同期の性能方針

アプリのJS実行は約200msで、体感の待ち時間はほぼ**バックエンドへの往復回数**で決まる。

- **起動は1往復**（`bootstrap`）。ログイン中のユーザー・事業部・**当月の一覧**を1つにまとめる。
- **一覧は月ごとに取得**する。月を切り替えたときだけ、その月の分を取りに行く
  （取得済みの月は先に描き、裏で最新に更新）。端末に残すキャッシュは直近3か月まで。
- **通信を待たずに前回の内容を描く**。起動時に白い画面を出さない。
- **外部スクリプトを起動経路に置かない**。同期の `<script src>` は、その通信が終わるまで
  アプリを止める（存在しないファイルでも、404が返るまで待たせる）。
- **申請・削除のあとに一覧を取り直さない**。保存済みのレコードをキャッシュへ直接加える。
- **1リクエスト内で同じシートを2度読まない**。`requireUser_` が読んだユーザー行を使い回す。
- **ドライブの走査は絞ってから行う**。ファイル名の採番は「同じ日・同じ申請者」で検索する。
- AI解析の所要時間は出力トークン数でほぼ決まる（4.1 の行数と呼び出し回数が調整点）。

## 5. データモデル

タブ名と1行目の見出しは日本語（シートを直接見る人向け）、JSON API・フロントエンドが使う
内部キーは英語で固定（外部連携を壊さないため）。シートの読み書きは**列の位置**で行い、
見出しは表示専用。`SCHEMA_VERSION` が変わったときに、全シートのタブ名・見出しを
まとめて現在の定義へ移行する（エディタから `migrateSheets` を手動実行しても同じ）。

**経費データ**（内部キー → 見出し）:
`id`→申請ID / `createdAt`→申請日時 / `applicant`→申請者 / `date`→利用日 /
`category`→科目 / `vendor`→支払先 / `amount`→金額 / `description`→摘要 /
`status`→状態 / `reviewedAt`→処理日時 / `reviewer`→処理者 /
`reviewComment`→却下理由・備考 / `imageUrl`→領収書URL /
`imageFileId`→領収書ファイルID / `applicantId`→申請者ID / `department`→事業部 /
`fareFrom`〜`fareCheck`（出発駅・到着駅・往復・回数・片道運賃・想定金額・運賃照合）

- `status` は新しい申請では常に `approved`、`reviewer` は「自動承認」。
- 末尾の運賃照合の7列は、かつての機能の名残。**新しい申請では空**。列の位置を
  過去の行とそろえるために定義だけ残している。

**ユーザー**:
`username`→ユーザーID / `displayName`→表示名 / `passwordHash`→パスワードハッシュ /
`salt`→ソルト / `role`→権限（`user` / `admin`）/ `active`→有効 / `createdAt`→登録日時 /
`department`→事業部（カンマ区切りで複数）

**事業部マスタ**: `name`→事業部名

**使われなくなったタブ**: 運賃マスタ・AI学習ログ・PL連携マッピング・PL連携スキップは、
過去の版で作られたもの。今のコードは読み書きしない（残っていても害はなく、不要なら削除してよい）。

## 6. API（POST は `text/plain` の JSON。認証系以外は token 必須）

CORS のプリフライトを避けるため、`Content-Type: application/json` ではなく `text/plain` で送る。

| action | 内容 |
| --- | --- |
| `status` | 認証が有効か・バックエンドの版（デプロイ後の疎通確認にも使う） |
| `setup` | 最初の管理者の作成（初回のみ） |
| `login` / `loginCode` | ID+パスワード／利用コードでログイン → `{token, user}` |
| `bootstrap` | 起動用。ユーザー・事業部・一覧を1往復で返す。`month` で月を絞る。残りが半分を切っていれば新しい `token` も返す |
| `list` | 一覧。`month`（`yyyy-MM`）でその月の分だけ。空は全期間 |
| `create` | 申請の作成。`record.imageBase64` があればドライブへ保存。保存済みのレコードを返す |
| `delete` | 取消（一般は自分の分、管理者は全件）。画像もゴミ箱へ |
| `analyzeReceipt` | AIレシート解析（日付・金額・店名・科目・摘要を返す） |
| `listUsers` / `upsertUser` / `issueAccessCode` | 利用者の一覧・更新・利用コードの発行/再発行（admin のみ） |
| `addDepartment` / `deleteDepartment` | 事業部の追加・削除（admin のみ） |

- **GET** `?token=...` → `{ ok:true, records:[...] }`。セッショントークンなら、一般は自分の分・
  管理者は全件。`SHARED_TOKEN` の値なら全件（分析ツールの定期取得向け、読み取り専用）。
- 詳細は `apps-script/README.md`。

## 7. デプロイ経路

| 対象 | 実体 | 反映方法 |
| --- | --- | --- |
| フロントエンド `expense-app/` | GitHub Pages | `main` への push で自動（`deploy-pages.yml`） |
| バックエンド `apps-script/Code.gs` | Google 側の Apps Script プロジェクト | `main` への push で自動（`deploy-apps-script.yml`）。シークレット3つが必要 |

バックエンドの自動デプロイは clasp を使い、`clasp pull` → ソースのみ差し替え →
`clasp push` → `clasp redeploy <既存デプロイID>` の順で行う。既存デプロイを新バージョンへ
更新するため、ウェブアプリURL（`.../exec`）は変わらない。マニフェストは取得したものを
押し戻すので、公開設定はCIで変更されない。デプロイ前に構文チェックと回帰テストを実行し
（失敗したらデプロイしない）、デプロイ後に `status` で疎通確認する。**疎通確認に失敗したら、
直前のバージョンへ自動でロールバックする。**

## 8. セキュリティ / 制約

- パスワード・利用コードは平文保存しない（ソルト付きSHA-256）。トークンはHMAC署名・30日で失効
  （使うたびに延長。コード再発行・パスワード変更で即失効）。
- 申請者名・申請者IDはサーバー側でセッションから強制し、なりすましを防止する。
- スプレッドシート・ドライブ自体の閲覧権限は Google 側の共有設定に従う
  （管理者＝シート所有者のみが直接閲覧できる構成を推奨）。
- 領収書画像は「リンクを知っている人は閲覧可」（4.4）。
- 申請時に、画像と内容は自組織の Google 環境へ送られる。AIの読み取りでは、画像が
  選んだプロバイダ（Gemini / Claude）へ送られる。Gemini の無料枠は入出力が学習に使われる
  ので、使わせたくない場合は有料枠または Claude を使う。
- WebアプリURLは、公開サイトには埋め込まない（公開サイトから読めると、未ログインで呼べる
  `loginCode` の宛先が知られるため）。案内文のリンクにURLを入れて配る。
- Apps Script の自動デプロイの `CLASPRC_JSON` は、当該Googleアカウントの Apps Script /
  ドライブを操作できる認証情報。リポジトリの書き込み権限を持つ範囲＝この権限を
  行使できる範囲になる点に注意する。

- 一覧のCSV出力。
