# 経費申請アプリ 仕様書

最終更新: 2026-08-03

## 1. 目的

経費の申請から確認・承認までをブラウザ上で完結させ、申請データを
**Google スプレッドシートにデータベース化**、**領収書画像を Google ドライブに保存**する。
ログインと権限管理（一般／管理者）を備え、蓄積データを実績管理・分析ツールから
読み込んで連携・分析できる状態にする。

## 2. システム構成

```
[利用者のブラウザ]                        [Google クラウド]
  経費申請アプリ (静的サイト)               ┌───────────────────────────┐
   - ログイン / セッション管理             │ Apps Script Web App       │
   - 画像OCR (Tesseract.js / 端末内)  ─┐   │  認証・権限チェック        │
   - 申請フォーム                      │   │  doPost: auth/create/     │
   - 個人 / 管理者ダッシュボード        ├──▶│   update/delete/users     │
   - localStorage キャッシュ           │   │  doGet : JSON（権限別）    │
                                       │   └───────┬───────────┬───────┘
                                       │           ▼           ▼
                                       │   スプレッドシート   Google ドライブ
                                       │   経費データ/ユーザー等  (領収書画像)
                                       │           │
[分析・実績管理ツール] ◀────────────────┘           │
   Looker Studio / BIツール / スプレッドシート集計 / JSON API / CSV
```

- フロントエンド: バニラ JS（`expense-app/`）。GitHub Pages で公開。レスポンシブ対応。
- バックエンド: Google Apps Script Web App（`apps-script/Code.gs`）。サーバー・GCP設定不要。
- データストア（1つのスプレッドシート内）。タブ名・見出しは日本語:
  - **経費データ** シート = 経費データ（1申請1行）
  - **ユーザー** シート = ユーザーアカウント（パスワードはソルト付き SHA-256 ハッシュ）
  - **事業部マスタ** シート = 事業部の一覧
  - **AI学習ログ** シート = AI解析の学習ログ（手修正の履歴・店舗別の補正記憶）
  - **運賃マスタ** シート = 電車賃の区間別片道運賃（照合の基準値）
  - Google ドライブ「経費領収書」フォルダ = 領収書画像（行に URL を保持）

### 2.1 動作モード

| モード | 条件 | 認証 | 保存先 |
| --- | --- | --- | --- |
| クラウド | ⚙️でWebアプリURLを設定 | ログイン必須 | スプレッドシート＋ドライブ（正本） |
| ローカル（試用） | 未設定 | なし（氏名入力のみ） | localStorage のみ |

クラウドモードで通信失敗した申請は端末内の再送信キューに退避し、「再同期」で反映する。

## 3. 認証・権限

### 3.1 認証方式
- ユーザーID＋パスワード。パスワードは「ユーザー」シートにソルト付き SHA-256 で保存。
- ログイン成功で **HMAC-SHA256 署名付きセッショントークン**（有効期限12時間）を発行。
  以降のリクエストはトークンを必須とし、サーバー側で毎回検証する。
- 初回接続時（「ユーザー」シートが空）は「初期設定」画面で最初の管理者を作成する
  （それまでは従来互換のオープンモード）。

### 3.2 権限（ロール）

| 操作 | 一般（user） | 管理者（admin） |
| --- | --- | --- |
| 経費の申請 | ✅（申請者名・事業部はセッションからサーバーが強制） | ✅ |
| 申請の閲覧 | 自分の申請のみ | 全申請 |
| 承認 / 却下 / 差戻（フローモード時のみ） | ❌ | ✅（承認者名もサーバーが強制） |
| 申請の削除 | 自分の申請（状態問わず・ミス時の自己取消） | 全件（ミス・重複申請の削除） ※いずれもシート行＋ドライブ画像を連動削除 |
| ユーザー管理（追加・無効化・PW再設定・事業部設定） | ❌ | ✅（自分自身の無効化・降格は不可） |
| パスワード変更（自分） | ✅ | ✅ |

### 3.3 承認モード

- **自動承認モード（既定）**: 申請は保存と同時に `approved` になる（承認者=「自動承認」）。
  承認フローは省略し、誤り・重複は管理者の削除で対応する。
- **フローモード**: スクリプトプロパティ `AUTO_APPROVE` を `"false"` に設定すると、
  従来の 申請中 → 承認/却下/差戻 フローが有効になる（将来のスケール時に復活可能）。
  アプリUIはモードに応じて操作ボタンを自動で出し分ける。

## 4. 機能要件

### 4.1 画像解析（レシート読み取り・2段構え）
- レシート／領収書画像をアップロード（クリック選択・ドラッグ＆ドロップ）。**画像は任意**。
- **3段フォールバック**: AI解析 → 端末内OCR → 手入力。
- **①AI解析（高精度）**: GAS に AIキー設定時、画像解析＋構造化出力で
  **金額・日付・店名・科目・摘要** を抽出しフォームへ自動入力。プロバイダは設定で選択:
  - **Gemini（推奨・無料枠可）**: `GEMINI_API_KEY`。モデルは `GEMINI_MODEL`（未設定なら現行の flash 系を新しい順に自動で試す）。
    無料枠は入力/出力が学習に利用される点に留意。
  - **Claude**: `ANTHROPIC_API_KEY`。モデルは `OCR_MODEL`（既定 `claude-opus-4-8`）。学習利用なし。
  - 両方設定時は Gemini 優先（`OCR_PROVIDER` で切替）。
- **②端末内OCR（フォールバック）**: AI未設定時・失敗時は Tesseract.js。
  前処理（拡大→グレースケール→大津の二値化）と単一ブロック解析で精度を強化。
  金額抽出は「合計/総額/請求」優先、「お預り/お釣り/現金」等を除外。
- **③手入力**: いずれも読み取れないとき。抽出結果はフォームへ自動入力され手修正可能。

#### 4.1.1 手修正の学習（店舗別の補正記憶）

手修正した内容を店舗ごとに蓄積し、次回同じ店舗のレシートで再利用する。
モデルの再学習（ファインチューニング）ではなく、「AI学習ログ」シートへの
記録とその再利用で実現する。

- **記録**: AI解析を使った申請の保存時に、「AIの読み取り値」と「利用者が確定した値」を
  1行記録する。店名が読み取れなかった申請は次回の手がかりにできないため記録しない。
- **①辞書補正**: 同じ店舗の確定値で **店名・科目・摘要** を自動補正する。
  ルールベースのため結果がぶれない。金額・日付は申請ごとに変わるため辞書では触らない。
  摘要は同じ内容が2回以上確定した場合のみ採用する（単発の摘要を使い回さない）。
- **②誤読事例のフィードバック**: その店舗で過去に誤読した金額・日付・店名を
  **今回のAIが再び同じ値で読んだ場合に限り**、実際の誤り（と当時の書き起こし）を
  プロンプトに添えて **1回だけ読み直す**。「小計を合計と取り違える」等の
  フォーマット固有の失敗に効く。
  読み直しはAI呼び出しが1回増えるため、誤読履歴があるだけでは行わない
  （履歴だけを条件にすると、よく使う店舗ほど毎回2回呼ぶことになり遅くなる）。
  今回の読み取りが過去の誤読と違う値なら、読み直しても直せる根拠が無いため行わない。
- **店名の表記ゆれ**: 全半角・空白・法人格・記号を吸収した照合キーで同一店舗を判定する。
  AIが店名を誤読した回の履歴からも確定名にたどり、同一店舗の履歴をまとめて参照する。
- **限界**: 画像が暗い・ブレる等で何も読み取れなかったレシートは、次回と結びつける
  手がかり（店名）が無いため学習できない。撮り直し・回転補正で対応する。
- **管理**: 管理者ダッシュボードの「AI解析の学習データ（店舗別）」で内容を確認でき、
  店舗単位で削除（学習のやり直し）ができる。申請データそのものは消えない。
  参照は直近600件。

### 4.2 経費申請
- 入力: 日付（必須）、科目（必須）、事業部、支払先、金額（必須・1円以上）、摘要。
- **領収書画像は任意**（画像なしでも申請可能）。
- **事業部は申請ごとにプルダウンで選択可能**（事業部マスタから選択）。
  未選択の場合は自分のプロフィールの事業部が自動で入る。
- 科目: 交通費／交際費／会議費／消耗品費／通信費／宿泊費／その他。

### 4.2.0 交通費の運賃照合（電車賃）

電車賃は領収書が出ないため、**区間から想定運賃を出して申請額と突き合わせる**。

- **入力**: 科目が「交通費」のときだけ申請フォームに区間欄が出る。
  出発駅 / 到着駅 / 片道・往復 / **回数**（まとめて申請する場合に対応。上限60回）。
- **想定金額** = 片道運賃 × (往復なら2) × 回数。
- **照合の流れ**:
  1. **運賃マスタに登録済みの区間** → その値で即照合（Web検索なし・結果が一定・課金なし）
  2. **未登録の区間** → Gemini の Google 検索グラウンディングで
     「大人1名・通常運賃・IC片道」を調べ、経路と出典URLを添えて返し、
     **運賃マスタへ登録**する（次回以降は 1 になる）
  3. 運賃が確認できなければ推測値は入れず、路線検索で調べて手入力するよう案内する
- **表示**: 想定金額の内訳・経路・出典リンクを出し、申請額と比較して
  一致（緑）／差額あり（黄）を示す。金額が空なら「金額に反映」で入力できる。
  往復・回数を変えたときは再検索せず、照合済みの片道運賃で計算し直す。
- **判定の確定はサーバー側**: 保存時に片道運賃を運賃マスタから取り直して
  想定金額を再計算するため、申請者側で運賃を書き換えることはできない。
  結果は `fareCheck` に次のいずれかで残る。
  - `match` … 申請額 = 想定金額
  - `diff` … 申請額 ≠ 想定金額
  - `registered` … この申請額から運賃マスタへ登録した（下記）
  - `unchecked` … 区間はあるが、マスタにも無く申請額からも割り出せない
- **申請からの自動登録**: 未登録の区間が申請されると、**申請額から片道運賃を
  割り戻して運賃マスタへ登録する**（`片道運賃 = 申請額 ÷ (往復なら2) ÷ 回数`）。
  運用しながら区間が貯まり、2回目以降の同じ区間は自動で照合される。
  - 登録の元になった申請は `registered` とし、`match` にはしない。
    自分の申請額で自分を照合しても確認したことにならないため。
  - 運賃マスタには照合方法として `申請（申請者名）` を記録する。
    最初の1件は誰も確認していない値なので、管理者が承認前に金額を確かめる。
  - **割り切れない金額**（運賃以外が混ざっている・回数が実態と合わない）と、
    **上限を超える高額**（桁の打ち間違い。上限 `FARE_UNIT_MAX` = 100,000円）、
    金額0の申請は登録しない（`unchecked` のまま残す）。
  - 既に登録済みの区間は**上書きしない**。申請額との差は `diff` として出す。
- **ダッシュボード**: 一覧のカード・表に「🚃 一致 / 差額あり / 新規登録 / 未照合」
  バッジと区間（例: `新井薬師前→武蔵浦和 往復 ×2回`）を表示。管理者一覧は
  **運賃照合フィルタ**（すべて／差額あり／新規登録／未照合／一致）で絞り込める。
- **区間キー**: 駅名は全半角・空白・末尾の「駅」を吸収して照合し、
  **上りと下りは同じ区間**として扱う（運賃が同じため）。
- **精度の担保**: Web照合はAIの検索結果なので外すことがある。出典URLを併記して
  人が確認できるようにし、誤りは管理者が運賃マスタで上書きできる。
  出典が取れなかった場合（検索が使われずAIの記憶で答えた場合）は警告を出し、
  運賃マスタの照合方法に「出典なし・要確認」と記録する。
  ローカル（試用）モードではWeb照合は使えない（区間の入力のみ可）。
- **AIを使わない導線**: 区間欄と運賃マスタの追加フォームに
  **路線検索を開くリンク**を置く。駅名を入れるとリンクが有効になり、
  自分のブラウザで運賃を確認して入力・登録できる（無料・AI不要）。
  検索サイトの自動読み取りは各社の規約で禁止されているため実装しない。
- **Google検索グラウンディングは有料機能**: Gemini APIの無料枠では割当が0
  （`limit: 0`）で使えない。そのため **Web照合は既定で無効**とし、課金を有効に
  した環境でのみスクリプトプロパティ `FARE_WEB_LOOKUP` に `true` を設定して使う。
  有効な状態で割当不足を検知したときは自動で `false` を保存し、以降は運賃マスタ
  のみの運用へ切り替える（何度も失敗して待たされないため）。
- **運賃マスタのみの運用**: 未登録の区間は**エラーにせず**、「路線検索で調べて
  金額を入力してください」と案内する（申請は進められる）。その申請額が運賃マスタ
  への登録値になるため、以降の同じ区間は自動で照合される。
- **初期設定の一括登録**: 運賃マスタに「まとめて登録」欄があり、1行
  `出発駅, 到着駅, 片道運賃[, 経路]` で複数区間をまとめて登録できる。
  カンマ・タブ・全角カンマに対応。読めない行は行番号と理由を返し、
  読めた行だけ登録する（途中で止めない）。

### 4.2.0.1 運賃マスタ

- `運賃マスタ` シートで区間ごとの片道運賃を管理する。
- 管理者ダッシュボードの「運賃マスタ（電車賃の照合基準）」で一覧・
  **運賃の直接編集**（運賃改定・AIの誤りの訂正）・削除・手動追加ができる。
- 削除するとその区間は次回の照合で再びWebから取り直される。
- 手修正した行は「照合方法」に手動と実行者名が入り、Web照合と区別できる。

### 4.2.1 事業部マスタ
- 事業部は「事業部マスタ」シートで管理し、申請フォーム・ユーザー登録のプルダウンに反映。
- 初期値: BAR / 人材 / 運送 / 本部 / ARTGRAGE / クリニック / GoonerHouse。
- 管理者ダッシュボードの「事業部の管理」から追加・削除が可能。
  削除しても過去の申請データの事業部名は保持される（選択肢から外れるだけ）。

### 4.2.2 領収書の保管（Google ドライブ）
- フォルダ体系: `経費領収書/<事業部>/<yyyy-MM>/`。事業部未設定の申請は「未設定」フォルダへ。
- **事業部フォルダ**: 事業部の追加と同時に自動作成。事業部を削除しても
  **フォルダと保存済み画像は残す**。
- **月フォルダ**: 申請保存時に経費の日付の月フォルダを自動作成（抜け漏れなし）。
  加えて `setupMonthlyFolderTrigger()` を一度実行すると、**毎月末（28日）に
  翌月分のフォルダを全事業部へ事前生成**するトリガーが登録される。
- **ファイル名規則**: `日付_申請者_採番.jpg`（例: `2026-07-15_山田太郎_001.jpg`）。
  採番は同じ日付・同じ申請者の中で 001 からの連番。申請の削除時は画像も
  ゴミ箱へ連動（従来どおり）。

### 4.2.3 領収書の閲覧（ダッシュボード）

個人・管理者の両ダッシュボードで、一覧の表示形式を切り替えられる。

- **カード表示（既定）**: 1申請1カード。左に領収書サムネイル、右に科目・状態・金額・
  支払先・摘要・操作ボタン。画像が無い申請は同じ大きさの「領収書なし」枠を出す。
- **表表示**: 従来の表。「領収書」列に小さなサムネイルを表示する。
- 選択した表示形式は端末に記憶する（localStorage）。
- **領収書ビューア**: サムネイルをクリックすると拡大表示。日付・金額・申請者・事業部・
  科目・支払先を併記し、◀▶（← →キー）で**表示中の一覧の領収書だけ**を順に送れる。
  Esc または背景クリックで閉じる。「ドライブで開く」で原本を別タブ表示。
- **画像の取得経路**: まず Drive のサムネイルURL（`thumbnail?id=...&sz=w...`）を直接読む。
  領収書はGAS実行アカウントのドライブにあるため、**保存時に「リンクを知っている人は
  閲覧可」に設定**して直リンクが通るようにしている（`shareReceiptFile_`）。
  共有できなかった場合（組織のポリシーで外部共有が禁止されている等）は
  **アプリ経由（`receiptImage`）で自動的に取り直す**ため、表示自体は必ずできる。
  取得した画像は画面を開いている間キャッシュする。どちらでも取得できない場合のみ
  「表示できません」の枠を出す。
- **共有設定を入れている理由**: 共有しないと所有者以外は必ず直リンクが403になり、
  画面に出ている領収書の枚数だけアプリ経由の取得が走る（1枚＝1往復）。
  所有者本人だけは直リンクが通るため、この遅さは管理者からは見えない。
  トレードオフとして、**URLを知っていれば認証なしで画像を閲覧できる**状態になる。
  許容できない運用では `shareReceiptFile_` を無効化すれば従来の挙動（遅いが所有者に
  閉じる）へ戻せる。既存の画像は `shareExistingReceipts` の手動実行で揃う。

### 4.3 個人ダッシュボード
- **月次表示**: 既定は当月。◀▶で月移動、月指定、「全期間」切替が可能。
- 自分の申請一覧・集計（申請件数、申請中、承認済み金額、申請中金額）。
- 領収書のサムネイル表示・拡大表示（4.2.3）。表示形式（カード／表）の切替。
- 申請中の取消、却下理由の確認、パスワード変更。

### 4.4 管理者ダッシュボード
- **月次表示**: 既定は当月。◀▶で月移動、月指定、「全期間」切替が可能。

### 4.6 起動と同期の性能方針

アプリのJS実行は約200msで、体感の待ち時間はほぼ**バックエンドへの往復回数**で決まる。
そのため次を方針とする。

- **起動は1往復**（`bootstrap`）。`status` → `me` → 一覧取得の3往復を1つにまとめる。
  画面とバックエンドは別々に配信されるため、バックエンドが古い場合は
  従来の3往復へ自動でフォールバックする（アプリ側は動き続ける）。
- **通信を待たずに前回の内容を描く**。クラウドモードでもキャッシュを先に描画し、
  応答が返った時点で差し替える。起動時に白い画面を出さない。
- **外部スクリプトを起動経路に置かない**。OCR（Tesseract.js）はAIキー未設定時の
  フォールバックにしか使わないため、`index.html` では読み込まず、必要になった
  時点で動的に読み込む。同期スクリプトとして置くと、その通信が終わるまで
  アプリのJSが実行されない。
- **領収書画像は直リンクで読ませる**（4.2.3）。アプリ経由の取得は1枚＝1往復になる。
- **画像の認可でシート全体を読まない**。`receiptImage` は対象の1列だけを引いて
  該当行を特定する。一覧表示では画像の枚数だけ呼ばれるため、ここが効く。
- **申請の保存も1往復**。`create` は保存済みのレコードを返すので、アプリは
  それを一覧へ加える。保存後に一覧を取り直すと往復が倍になり、そのたびに
  全期間の申請をダウンロードすることになる。
- **1リクエスト内で同じシートを2度読まない**。`requireUser_` が読み取った
  ユーザー行の `department` を使い回す。運賃マスタも、未登録と確認済みなら
  `appendFare_` で追記のみ行う。
- **ドライブの走査は絞ってから行う**。領収書のファイル名を採番するとき、
  月フォルダ全体ではなく「同じ日・同じ申請者」で検索してから数える
  （全走査だと、その月の申請が増えるほど保存が遅くなる）。

AI解析の所要時間は**出力トークン数**でほぼ決まる。画像の縮小・思考の無効化・
`temperature:0`・`maxOutputTokens` は適用済みで、残る調整点は
書き起こし行数（`RECEIPT_RAW_TEXT_MAX_LINES`）とAI呼び出し回数（4.1 の読み直し条件）。

## 5. データモデル

**シートを直接見る人向けにタブ名と1行目の見出しは日本語**、JSON API・CSV・
フロントエンドが使う内部キーは英語で固定する（外部連携を壊さないため）。
シートの読み書きは列の位置で行い、見出しは表示専用。
旧版で作られた英語タブ・英語見出しは、次回アクセス時に**全シートまとめて**
自動で日本語へ移行される（手動の移行作業は不要）。
各シートは本来「使われたとき」にしか触られないため、AI学習ログのように
特定の操作でしか使わないタブが取り残されないよう、スクリプトプロパティ
`SCHEMA_VERSION` で版を管理し、版が変わったときに一度だけ全シートを移行する。
エディタから `migrateSheets` を手動実行しても同じ移行ができる。

**経費データ**（内部キー → 見出し）:
`id`→申請ID / `createdAt`→申請日時 / `applicant`→申請者 / `date`→利用日 /
`category`→科目 / `vendor`→支払先 / `amount`→金額 / `description`→摘要 /
`status`→状態 / `reviewedAt`→処理日時 / `reviewer`→処理者 /
`reviewComment`→却下理由・備考 / `imageUrl`→領収書URL /
`imageFileId`→領収書ファイルID / `applicantId`→申請者ID / `department`→事業部 /
`fareFrom`→出発駅 / `fareTo`→到着駅 / `fareRound`→往復 / `fareTrips`→回数 /
`fareUnit`→片道運賃 / `fareExpected`→想定金額 / `fareCheck`→運賃照合

**ユーザー**:
`username`→ユーザーID / `displayName`→表示名 / `passwordHash`→パスワードハッシュ /
`salt`→ソルト / `role`→権限 / `active`→有効 / `createdAt`→登録日時 /
`department`→事業部

**事業部マスタ**: `name`→事業部名（初期値 BAR / 人材 / 運送 / 本部 /
ARTGRAGE / クリニック / GoonerHouse）

**運賃マスタ**: `key`→区間キー / `from`→出発駅 / `to`→到着駅 / `fare`→片道運賃 /
`route`→経路 / `source`→出典URL / `checkedAt`→照合日時 / `checkedBy`→照合方法

**AI学習ログ**: `createdAt`→記録日時 / `vendorKey`→店舗キー /
`aiVendorKey`→店舗キー（AI読取）/ `vendor`→店名（確定）/ `date`→利用日（確定）/
`amount`→金額（確定）/ `category`→科目（確定）/ `description`→摘要（確定）/
`aiVendor`〜`aiDescription`→各項目の（AI読取）/ `corrected`→修正された項目 /
`applicantId`→申請者ID / `rawHead`→書き起こし（先頭）

- `status`: `pending` / `approved` / `rejected`。`role`: `user` / `admin`。
  （シート上の見出しは日本語だが、値そのものは英語のまま）

## 6. API（POST は text/plain の JSON。認証系以外は token 必須）

| action | 権限 | 内容 |
| --- | --- | --- |
| `status` | 不要 | 認証が有効か（初期設定済みか）を返す |
| `bootstrap` | 不要 | 起動用。`status` + `me` + 一覧を1往復で返す。トークンが無効でもエラーにせず `user: null` を返す（ログイン画面へ進むのに追加の往復を要さないため） |
| `setup` | 不要（初回のみ） | 最初の管理者を作成しトークン発行 |
| `login` | 不要 | 認証してトークン発行 |
| `me` | user | セッション検証・ユーザー情報 |
| `changePassword` | user | 自分のパスワード変更 |
| `create` | user | 申請作成（画像base64があればDrive保存） |
| `update` | admin | 承認・却下・差戻 |
| `delete` | user/admin | 取消（userは自分の申請中のみ） |
| `listUsers` / `upsertUser` | admin | ユーザー管理 |
| `listDepartments` | user | 事業部マスタ取得（プルダウン更新用） |
| `addDepartment` / `deleteDepartment` | admin | 事業部マスタの追加・削除 |
| `receiptImage` | user/admin | 領収書画像をアプリ経由で取得（userは自分の申請の画像のみ） |
| `lookupFare` | user | 区間の運賃照合（運賃マスタ優先、未登録ならWeb検索して登録） |
| `listFares` / `upsertFare` / `deleteFare` | admin | 運賃マスタの一覧・上書き・削除 |
| `analyzeReceipt` | user | AIレシート解析（AIキー設定時のみ。過去の学習を自動適用） |
| `listVendorMemory` / `deleteVendorMemory` | admin | AI解析の学習データの確認・店舗単位の削除 |
| GET `?token=` | user/admin | JSON取得（userは自分の分のみ） |

分析ツール向け: スクリプトプロパティ `SHARED_TOKEN` を設定すると、
GET `?token=<SHARED_TOKEN>` で全件を読み取り専用取得できる（Looker Studio等の定期取得用）。

主なスクリプトプロパティ: `AUTO_APPROVE`（`"false"`で承認フロー有効。既定は自動承認）、
`SPREADSHEET_ID` / `DRIVE_FOLDER_ID` / `AUTH_SECRET`（自動保存）、`SHARED_TOKEN`、
`GEMINI_API_KEY`（AI解析・運賃のWeb照合に共通で使用）、`GEMINI_MODEL` / `FARE_MODEL`
（モデルの固定。未設定なら現行の flash 系を新しい順に自動で試す）。

保存先は共有ドライブへ移行可能（ファイルIDは移動しても不変のため設定変更不要。
GAS実行アカウントを共有ドライブの「コンテンツ管理者」以上にすること）。

### 4.6 デプロイ経路

| 対象 | 実体 | 反映方法 |
| --- | --- | --- |
| フロントエンド `expense-app/` | GitHub Pages | `main` への push で自動（`deploy-pages.yml`） |
| バックエンド `apps-script/Code.gs` | Google 側の Apps Script プロジェクト | 既定は手動デプロイ。`deploy-apps-script.yml` にシークレットを設定すれば自動 |

`Code.gs` はプロジェクトの写しであり、リポジトリとプロジェクトの間に自動の
つながりは存在しない。自動デプロイは clasp（Apps Script CLI）を使い、

1. `clasp pull` で現行プロジェクトを取得（`appsscript.json` を含む）
2. ソースのみ差し替え（反映先はプロジェクト側のファイル名に合わせる）
3. `clasp push` → `clasp redeploy <既存デプロイID>`

の順で行う。既存デプロイを新バージョンへ更新するため、ウェブアプリURL
（`.../exec`）は変わらない。マニフェストは取得したものを押し戻すので、
公開設定（アクセスできるユーザー・実行するユーザー）はCIで変更されない。
デプロイ前に構文チェックと回帰テストを実行し、失敗時はデプロイしない。

## 7. セキュリティ / 制約

- パスワードは平文保存しない（ソルト付きSHA-256）。トークンはHMAC署名・12時間で失効。
- 申請者名・承認者名はサーバー側でセッションから強制し、なりすましを防止。
- スプレッドシート・ドライブ自体の閲覧権限は Google 側の共有設定に従う
  （管理者=シート所有者のみが直接閲覧可能な構成を推奨）。
- 領収書画像のアプリ経由取得（`receiptImage`）は、シートに登録済みのファイルIDのみ許可し、
  一般ユーザーは自分の申請の画像に限定する（任意のファイルIDは読み出せない）。
- ローカルモードは試用向けで認証なし。データは端末・ブラウザ間で共有されない。
- OCR は端末内処理。申請時に画像・内容は自組織の Google 環境へ送信される。
- Apps Script の自動デプロイを有効にする場合、GitHub Secrets に置く `CLASPRC_JSON` は
  当該Googleアカウントの Apps Script / ドライブを操作できる認証情報である。
  リポジトリの書き込み権限を持つ範囲＝この権限を行使できる範囲になる点に注意する。
